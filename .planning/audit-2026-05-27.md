## Scope
Complete audit across all layers of Qunt Edge following the teams/dashboard visual alignment and build fix. Builds on the prior launch-readiness audit (2026-04-26) — this report focuses on **new findings** and **unresolved items** from that baseline.

## 1. Build & Deployment Config

### CRITICAL: Node version mismatch
- **Dockerfile**: `FROM node:20-slim` — Node 20
- **Dockerfile.bun**: `FROM oven/bun:1 AS base` then `FROM node:20-slim` — Node 20
- **nixpacks.toml**: `nodejs_20`
- **`.nvmrc`**: `22`
- **`package.json` engines**: `node >=22.12.0`

All three Docker/deploy configs pin Node 20, but `.nvmrc` and `engines` require >=22.12.0. Node 20 went EOL 2026-04-30. **Fix: update all Dockerfiles + nixpacks.toml to Node 22.**

### Dockerfile.bun — NEXT_TELEMETRY_DISABLED commented out
Line 51: `# ENV NEXT_TELEMETRY_DISABLED=1` — commented out. Should be enabled in production builds.

### nixpacks.toml — pinned dependencies outdated
- `nodejs_20` (should be `nodejs_22`)
- `pnpm` not pinned (relies on auto-detect). If build environment has a different pnpm version, lockfile mismatches may occur.

### PM2 ecosystem.config.cjs — uses Bun runtime
`script: "bun", args: "run start"` — Uses Bun as the process runtime, but both Dockerfiles use node. If deploying via PM2 with Node, this will fail because `bun` won't be available. If deploying via Bun Dockerfile, this is fine. **Verify runtime consistency between deployment method and ecosystem config.**

### Prebuild step clears TS build cache
`clean-build-artifacts` script (likely deletes `tsconfig.tsbuildinfo` + `.next/`). This means every full build is cold — no incremental TS caching. Intentional for CI but slows local rebuilds.

### `typescript: { ignoreBuildErrors: true }` in next.config.ts
TS errors never fail the build. While the `npm run typecheck` command exists, this means CI pipelines that run `npm run build` won't catch regressions unless `typecheck` is wired into the CI pipeline explicitly.

## 2. Auth & Security

### CSP — missing production connect-sources
`lib/security/csp.ts` defines connect-src for dev (localhost, vercel.live) but **missing production origins** for:
- `*.whop.com` (payments)
- `resend.com` (email)
- Any API analytics endpoints (PostHog, Langfuse if self-hosted)
- Vercel blob/store URLs if used

**The CSP will block these in production unless `NEXT_PUBLIC_CSP_REPORT_ONLY=true` is set and the report-only mode catches violations before strict mode.**

### proxy.ts ALLOWED_ORIGINS — domain typo?
`lib/security/cors.ts` likely defines allowed origins. Need to verify the domain matches actual deployment domain (last known: `quntedge.com` but needs confirmation).

### Timing-safe cron comparison — fixed in Phase 1
The prior audit notes that `proxy.ts` cron-token comparison is now timing-safe for both bearer tokens and the `x-vercel-cron` header. **Confirmed: uses crypto.timingSafeEqual.**

### Auth guard layer is solid
- `server/authz.ts` provides `requireUser()`, `requireAdmin()`, `isAdminUser()` 
- Routes use `withRateLimited` pattern consistently (27 routes)
- Environment variable validation happens via Zod schema in `lib/env.ts`
- Supabase SSR client is properly implemented in `server/auth.ts`

### 17 `as any` usages in `app/` directory
Violates the AGENTS.md anti-pattern rule. Specific locations need assessment:
- `app/api/debug-data/route.ts` — uses `as any` (this is the file that had the syntax error)
- Various API routes and components

### 86+ `console.log` calls in `app/`
The prior audit baseline was 945 ESLint warnings. `console.log` violations are a subset. Sources include:
- API route handlers (debug logging)
- Component files
- `server/journal.ts` uses `console.error`

## 4. API Routes & Server Actions

### Route handler inventory
- 37 GET, 32 POST, 2 PUT, 2 PATCH, 5 DELETE, 1 OPTIONS
- 61 route handlers total
- 25+ API route directories
- 8 use `withRateLimited` wrapper (should audit the rest — many POST/PATCH/DELETE handlers are not rate-limited)

### debug-data/route.ts syntax error (FIXED)
Missing closing braces caused Vercel build failure. Root cause: the catch callback `(error) => { ... },` was missing `})` to close both the catch body and the `.catch()` call. **Fixed.**

### `_utils` directory under `app/api/`
Contains shared API utilities but is accessible as a route segment due to Next.js file conventions. Should be moved to `lib/` or prefixed with underscore differently.

### Email API route (`/api/email/*`)
Has its own bearer/secret validation — correctly classified as a public webhook route in proxy.ts so Supabase auth doesn't block it.

### Webhook handlers
- `/api/whop/webhook` — proper signature verification expected
- `/api/ready` — health check, publicly reachable
- `/api/email/welcome` — public webhook with bearer auth

### Server actions pattern
- 62 files across `server/` directory
- Use `'use server'` directive
- Mix of cached reads (`'use cache'`) and mutation patterns
- Some actions do both read + write, which makes caching unclear
